# Mining design

Status: proposed architecture; documentation only. Read `docs/mining/discovery.md` first. All paths are repository-relative; new paths below are proposed, not existing implementations. Decisions and example balance values here are design proposals, not playtested tuning.

## Approach and scope

Use one data-driven `MiningService` for every ore, shared by the local sandbox and the authoritative online region. Keep definitions, simulation and presentation separate. A service plus small adapters fits existing Fishing/Cooking ownership without extracting a generic gathering framework from those specialized games. Per-ore scripts duplicate logic; a cross-skill framework would expand this task unnecessarily.

The proposed traditional loop is: click a deposit, approach it, repeatedly attempt extraction, gain one ore and XP on success, then leave the deposit depleted until respawn. Failure grants nothing and schedules another attempt. Success/depletion ends all sessions on that deposit; players click again after respawn. No new inventory, item registry, XP curve, modal minigame, tool slot, or combat-equipment rules.

## Definitions and catalog constraints

New `godot_client/data/mining.json` contains `schema_version: 1`, `ores: []` and `pickaxes: []`. This is activity metadata, joined to existing `GameData` items by ID; names, icons, material and inventory behavior stay in `godot_client/data/items.json`.

| Record | Required fields and validation |
| --- | --- |
| Ore | `item_id` (unique existing integer ID), `required_level` (integer 1–100), `xp_reward` (positive integer, at most `SkillProgression.MAX_EXPERIENCE`), `success` (parameters below), `respawn_seconds` (finite, >0), `node_scene` (resolvable scene using the shared `MiningDeposit` script), `visual` (`available` and `depleted` texture paths). |
| Ore success | `p_at_unlock`, `p_at_mastery` (finite, `0 < p_at_unlock <= p_at_mastery <= 1`), `mastery_levels` (integer 1–99), `curve_exponent` (finite, >0). Each ore owns these independently of catalog tier and other ores. |
| Pickaxe | `item_id` (unique existing integer ID), `required_level` (integer 1–100), `attempt_interval_seconds` (finite, 0.25–10.0). No copied item statistics or inferred IDs. |

Eligible content candidates already exist: Bronze 235, Iron 239, Blacksteel 246, Mithril 249, Adamantite 252 and Coal 329. These are candidates, not an approved unlock/reward roster. Steel Ore 242 is historical and excluded; Steel comes from Iron + Coal. Starforged Ore 256 remains Golem Titan-only. Add `AcquisitionRules.can_mine(item: Dictionary) -> bool` in `godot_client/scripts/acquisition_rules.gd`: reject historical/non-generic materials, `boss_material`, top-tier materials and explicit boss/pending-only policies; never reuse `can_drop()` as mining permission. Inclusion in `ores` is also required. Preserve `godot_client/data/acquisition.json` policy.

**Catalog prerequisite:** no actual pickaxe item exists. Keep production `pickaxes` empty until separately authorized catalog work supplies real item IDs and acquisition. Do not substitute swords/rods, reserve invented IDs, or add placeholder items. Empty tool definitions produce a clear unavailable result. The architecture is buildable; playable Mining cannot be activated until this prerequisite and visual/content bindings are resolved.

Choose the fastest owned, Mining-eligible pickaxe from the backpack or equipped weapon, breaking equal intervals by ascending item ID. Carried tools do not need Attack level; equipping still uses `godot_client/scripts/equipment_progression.gd`. Tools are reusable. Lock the choice for a session; losing it cancels, changing tools requires restart and a full new interval. No special Mining equipment slot.

## Aetheria extraction rules

For Mining level `L`, ore requirement `R`, and ore parameters:

```text
L < R: reject before any attempt
u = clamp((min(L, 100) - R) / mastery_levels, 0, 1)
p = p_at_unlock + (p_at_mastery - p_at_unlock) * u ^ curve_exponent
success = server_rng.randf() < p
```

Illustrative Bronze-only tuning: ID 235, level 1, 35 XP, probabilities 0.22→0.68 over 30 levels, exponent 1.25, respawn 12.0 seconds. A hypothetical interval setting of 2.4 seconds gives expected extraction time `interval / p`: 10.91 seconds at unlock, 3.53 at mastery (excluding travel/respawn). This does not define a pickaxe item. Other ores can use any independent requirements/parameters. An ore unlocked at 100 uses its unlock probability; never divide by `100-R`. These are original proposed values, not OSRS rates; measure earned XP/hour before final tuning.

Wait a full pickaxe interval before the first roll and every subsequent roll. Use the host simulation clock, not the 0.6-second combat tick, wall-clock timestamps, client timers or animation callbacks. Accept only finite positive deltas, clamp each advance to 0.25 seconds, make at most one attempt per character per advance, and schedule the next deadline from the current clock; stalls never produce a burst of rewards. Starting the same active target again cannot reset/shorten its deadline. Randomness is injected for deterministic tests and owned only by the authoritative simulator.

Recheck alive/connected status, combat/casting, target, position, range plus line of sight, both level requirements, chosen-tool ownership and deposit generation before every roll. Movement/attack/cast/travel/new activity/tool loss/damage/death/disconnect cancels Mining; a persistence freeze pauses it without accumulated catch-up. Damage events cancel even if healing restores HP in the same step. Use the existing actor/state and collision queries. One success synchronously claims the available generation, marks it depleted, adds one item through `PlayerState.add_item()`, awards XP through `add_skill_experience("mining", xp)`, and closes competing sessions before any callback or await. Precheck stack count against `CharacterCodec.MAX_COUNT`; refusal leaves the deposit and XP unchanged. Report actual XP delta, including zero at cap.

## Shared state, transport and durability

Deposit identity is `(world_id, region_id, deposit_id)`; `deposit_id` is authored and stable, independent of node order/name. Runtime record: `{ore_item_id, state: available|depleted, generation, respawn_at}`. Increment `generation` on depletion and on respawn. Shared depletion lasts across player disconnect/travel while the region remains loaded. V1 world-state scope is one host process; restart/recreation resets deposits to available. Offline state is per loaded sandbox region. No cross-host lock or persistent deposit database is promised.

`mine_start` carries only `{deposit_id, deposit_generation}`; `mine_stop` has no extra fields. `Network.send_action()` already supplies ordered sequence numbers; extend `AuthoritativeRegion.SCHEMA` and its integer validation for `deposit_generation`. Reject unknown/disabled/wrong-region deposits and stale generations. Same-target repeats return success without changing timers; never accept client XP, items, probability, tool speed, RNG or elapsed time. Add `mine_start` to `world_host.gd` movement ordering and `online_world_view.gd` prediction reset handling.

Public snapshots add `deposits: [{deposit_id, ore_item_id, state, generation, respawn_at}]` and each actor's `gathering: {kind, deposit_id, tool_item_id, attempt_sequence, attempt_started_at, attempt_interval_seconds}` (empty when inactive). Private `activity` adds `kind: "mine"`, target/generation, next attempt deadline and stop reason. Use current snapshot sequence/region checks; reconcile countdowns to server time, and never restart an animation for duplicate samples. Repeated full deposit snapshots allow late join/recovery without a reliable event log; reuse bounded packet transport. Scan active sessions and depleted deposits only, with cached scene lookup; no scene traversal per frame. Process due attempts by deadline, server-shuffling ties to avoid permanent join-order advantage; recheck generation after each claim.

Inventory and XP become visible from committed character snapshots. Add `record_committed_total(skill: String, total: int) -> void` to the existing `godot_client/scripts/skill_training_session.gd`: first observation establishes a baseline, later positive deltas feed `record_event()`. The controller uses this for online Mining XP/hour; its session-owned baseline survives area travel via the existing retained training session and resets on a new login/session reset. Duplicate snapshots add nothing; historical XP on login is not a reward. Offline uses the reward callback. This is display telemetry, never a grant or second progression store.

Use existing prompt saves, fenced leases and idempotent operation IDs; never undo/replay a grant after an ambiguous save response. Deposit depletion is immediate transient state; already-earned inventory/XP persists through `CharacterCodec` and `WorldHost`. A crash before save acknowledgment can lose an uncommitted reward; persistent deposit/reward transactions across process crashes are outside V1. Save failure freezes attempts; on resume require a full interval. Removal/ownership loss cancels sessions. Character reconnect restores committed ore/XP but never resumes an old attempt.

Save migration: change `CharacterCodec.VERSION` to 2; decode versions 1 and 2, encode only 2. For version 1, default **only absent** `mining` XP to 0; malformed present Mining XP, missing pre-existing skills and unknown versions still reject. Version 2 requires all nine skills. `backend/accounts/views.py::validate_state()` currently accepts only version 1: allow 1 and 2 and update `backend/accounts/tests.py`. Deploy compatible backend before matched host/client; do not run an old host against upgraded saves or silently reset them on rollback.

## Extension and acceptance

A future ore requires an existing item ID, one validated definition and authored instances/visuals; no new Mining conditionals, class, command or reward code. Keep all resources environment-only. Ore unlock levels never derive from equipment tiers. Final unlock/XP/respawn rows, actual pickaxe IDs and approved art/placements are explicit content prerequisites, not invented here. See `docs/mining/implementation-plan.md` for incremental tests and rollout tasks.
